# قرار معماري — اعتماد Supabase لمشروع ملاعبي

## القرار
Supabase هو منصة البيانات والهوية:
- PostgreSQL: الجداول والعلاقات والقيود والفهارس.
- Supabase Auth: OTP بالهاتف، access token، refresh token، وإبطال الجلسات.
- Supabase Storage: مهيأ كخيار لاحق لصور الملاعب، وليس شرطاً لإطلاق Player MVP.
- NestJS: منطق الأعمال، التوفر، الحجز، الإلغاء، التقييم، وسياسات التطبيق.
- Player PWA: تتصل بـ NestJS فقط ولا تتصل بجداول قاعدة البيانات مباشرة.

## لماذا لا ننفذ الحجز من الواجهة عبر Supabase Data API؟
لأن الحجز يتطلب سياسة متسقة، حجز فترة 60 دقيقة، snapshots للسعر والسياسة، idempotency، معاملة واحدة لإنشاء booking وoccupancy، ومنع التداخل بقاعدة البيانات. إبقاء ذلك في API واحد يسهل الاختبار والتدقيق.

## حدود الثقة
- Publishable key: يمكن أن يظهر في الواجهة إن احتجنا SDK عام؛ لا يمنح صلاحية إدارية.
- Secret/Service Role key: خادم فقط، ولا يرفع إلى Git أو PWA.
- DATABASE_URL: خادم فقط، يفضّل Session Pooler للبيئات التي لا تملك IPv6.
- كل جداول المجال مفعّل عليها RLS، ولا توجد سياسات عامة للعميل. NestJS يتصل عبر حساب قاعدة البيانات الخلفي ويطبق تحقق المستخدم والصلاحيات.
- Supabase Auth user id يطابق public.users.id عبر trigger وFK.

## نقطة تشغيل حرجة
Supabase Phone Auth يحتاج مزود SMS. يجب التأكد من تغطية اليمن +967 وتكلفة الرسالة وSender ID وامتثال الاستخدام قبل تفعيل الإنتاج. لا تعتبر إعداد Supabase وحده دليلاً على نجاح SMS في اليمن.
